## 1. What this project is

**netintel** — a self-hosted DNS observability and network intelligence platform built on Technitium DNS Server, inspired first by a from-scratch "personal internet analytics" concept (v1) and then by Kentik's network observability platform (v2). Full history is in `docs/NETINTEL_V1_BIBLE.md`.

**Non-negotiables the whole project is built around:**
- Runs entirely on the user's LAN. No cloud, no telemetry, nothing phones home.
- **No mock mode, no fake data, ever.** This was removed on purpose after the user explicitly said it caused more confusion than value (commit `ac8fb60`). The server **refuses to start** without real `NETINTEL_TECHNITIUM_URL`/`NETINTEL_TECHNITIUM_TOKEN` in `.env`.
- Windows 10/11 and Linux only. No macOS.
- Node.js + TypeScript throughout (not Bun — deliberately chosen for Windows reliability).

## 3. How verification is done in this project (important methodology)

Since this sandbox has no real Technitium instance, every feature was verified using **throwaway, non-shipped seed scripts** that insert data directly into the SQLite DB (bypassing the collector), then the real server/API was exercised against that data, then the seed script was deleted and never committed. This is NOT the same as "mock mode" — it's how *I* (Claude) verify my own code before handing it over, the same way you'd use test fixtures. It should never leak into product code again.

**Pattern for any new feature:**
1. Write the real feature code.
2. `npm run build` (catches type errors — always do this first).
3. Write a `_verify_whatever.ts` script in `packages/server/` that seeds realistic data directly via Drizzle (must `import "dotenv/config"` first if it touches `db/client.ts`, or it'll write to the wrong DB path — this bit me once, see §6).
4. Boot the real server in the same shell session (background processes do **not** survive across separate tool calls in this sandbox — always seed + boot + curl + kill in one shell block).
5. Curl the real endpoints, confirm real numbers, not just "no error."
6. `rm` the verify script before committing. Never commit test artifacts.
7. Also periodically check `git status --short` before committing to make sure nothing stray got added.

Several real bugs were only found this way (SQL alias resolution, boolean bind params, an Advisor feedback loop, a device-identity double-counting bug, a poller crash-on-unreachable-Technitium bug). **Don't skip this step for new work.**

## 4. Current architecture

```
netintel/
  packages/
    shared/    — types, the 50-metric registry (shared by CLI + web), category taxonomy
    server/    — API (Hono), collector, analytics engine, alerting, advisor, capacity,
                 synthetics, reports, explorer query engine — see §5 for full module map
    cli/       — `netintel` command-line tool
  apps/
    web/       — dashboard (React + Vite + TanStack Router + Recharts + d3-force)
  docs/
    NETINTEL_V1_BIBLE.md   — original v1 spec: architecture, all 50 metrics, roadmap
    SETUP.md                — full network setup guide (topologies, DHCP, fallback configs)
    NETWORK_LOCKDOWN.md     — DoH/DoT/DoQ bypass-prevention guide
  packaging/
    linux/     — systemd service (EnvironmentFile=.env) + install.sh
    windows/   — NSSM service install.ps1 (also reads .env via cwd)
```

**Data flow:** Technitium (real instance, required) → `Poller` polls `/api/logs/query` + `/api/dhcp/leases/list` every 5s/30s → `ingestQueryLogEntry()` writes to `dns_events` + upserts `domains`/`domain_daily`/`client_daily` rollups → a 60s scheduler tick (`analytics/scheduler.ts`) runs ~10 different jobs (see §5) → API serves it all → React dashboard + CLI both consume the same REST API.

**Database:** SQLite via better-sqlite3 + Drizzle ORM, WAL mode. Schema in `packages/server/src/db/schema.ts`. **5 migrations applied so far** (`packages/server/drizzle/0000` through `0004`) — note migrations 0001–0004 were **hand-written**, not generated by `drizzle-kit generate`, because that tool had an unresolved tooling issue in this sandbox (silently exits after "Please install latest version of drizzle-orm" with no further error). If you need a new migration, either fix drizzle-kit's issue or keep hand-writing SQL + manually appending to `drizzle/meta/_journal.json` (see any of the existing 0001–0004 files as a template — the `_journal.json` format doesn't need matching `meta/000X_snapshot.json` files for the runtime migrator to work, only `drizzle-kit generate` needs those, and generate is broken anyway).

## 6. Known gaps and unverified assumptions — READ THIS BEFORE TOUCHING RELATED CODE

These are honestly documented in code comments too, but consolidated here:

1. **`alerting/actions.ts` — `block_domain` action.** Calls `/api/blocking/blocked/add` on Technitium. This endpoint path is a *guess* based on documented convention, **never confirmed against a live instance**. `/api/logs/query` was ALSO wrong until the user tested it live (needed `name`/`classPath` params, and the client IP field is `clientIpAddress` not `clientIp` — already fixed, see commit `53ab91f`). Expect `block_domain` might need the same kind of fix. It fails loudly/honestly if wrong (doesn't fake success), so it's safe to ship, but don't assume it works.

2. **Metric #21 (TTL) and #24 (Upstream Comparison).** `answerTtl` and `upstream` fields in `dns_events` are populated from `entry.answerTtl`/`entry.upstream` in the real collector — **unconfirmed whether Technitium's real API actually returns these fields.** `responseRtt` (latency) WAS confirmed present (only for Recursive lookups) after live testing — TTL/upstream have not been confirmed one way or the other yet. If you get access to a real instance, checking a raw `/api/logs/query` response for these two fields is high-value.

3. **`infrastructure/health.ts` — Windows behavior unverified.** `os.loadavg()` returns `[0,0,0]` on Windows by Node design (handled — reported as `null`, not faked). `fs.statfsSync` Windows support was uncertain at implementation time and is wrapped in try/catch (reports `null` on failure) — but never actually tested on a Windows box.

4. **`drizzle-kit generate` is broken in this sandbox.** Exits silently after a version-check warning with no further output. All migrations after the first were hand-written SQL. Worth revisiting if you have a different environment — might just work there.

5. **No Parquet/PDF write path failure has been extensively fuzz-tested** — the happy path is solidly verified (real files, round-tripped/rendered), but malformed/edge-case payloads haven't been thrown at it.

## 7. Bugs found and fixed during development (worth knowing so you don't reintroduce them)

- **SQL alias resolution** (`explorer/query-engine.ts`): SQLite couldn't resolve `value`/`bucket` aliases through drizzle's dynamic query builder in `ORDER BY`/`GROUP BY`. Fixed by repeating the actual expression instead of referencing the alias.
- **Boolean bind params**: better-sqlite3 rejects native JS `true`/`false` as bind parameters. Any raw `sql\`...\`` fragment with a boolean value needs `typeof v === "boolean" ? (v ? 1 : 0) : v` coercion first.
- **Device identity double-counting**: the ingest pipeline was calling the fuzzy identity-matching function (meant for reconciling DHCP lease signals) on every single DNS query, which doesn't clear its own merge threshold on IP alone — creating a new "device" per query. Fixed with a fast-path exact-IP lookup (`resolveDeviceIdByIp`) for the hot ingest path, keeping the fuzzy matcher only for actual DHCP sync.
- **Advisor feedback loop**: Advisor's own "correlated events" notifications were being pulled into its *next* correlation pass (since they're recent too), causing clusters to snowball every scheduler tick. Fixed by excluding Advisor's own `insights` category from its own input, and by only narrating clusters whose most recent member is <90s old (makes dedup fall out of time itself rather than needing fragile in-memory state).
- **Poller crash on startup**: if Technitium was unreachable when netintel started, the whole process used to `process.exit(1)`, taking the API/dashboard down too. Fixed — now retries connecting in the background every 15s while the API/dashboard stay fully usable against historical data.
- **Fetch calls could hang indefinitely** against an unreachable Technitium (no timeout on the original `fetch()` calls). Fixed with `AbortController` + 5-8s timeouts on all Technitium API calls.
- **Test-harness bugs (not product bugs, but easy to repeat if you're not careful):** background processes silently die across separate tool-call shell sessions in this sandbox (always chain seed+boot+test+kill in one block); a seed script that doesn't `import "dotenv/config"` writes to the wrong DB path since `db/client.ts` reads env vars at module-load time.

## 8. Environment / running this project

**No more shell exports.** Everything is `.env`-based now (added specifically per user request, replacing the original shell-export instructions):

```bash
cd packages/server
cp .env.example .env
# edit .env: set NETINTEL_TECHNITIUM_URL and NETINTEL_TECHNITIUM_TOKEN (both required)
```

Optional SMTP config in the same `.env` for alert-email/scheduled-report-email dispatch — see `.env.example` for the full variable list (also `packages/cli/.env.example` for `NETINTEL_API_URL`).

```bash
npm install
npm run build            # builds all 4 packages in order (shared -> server -> cli -> web)
cd packages/server && npm run db:migrate
npm run dev:server       # from repo root
npm run dev:web          # from repo root, separate terminal
```

Production install: `packaging/linux/install.sh` or `packaging/windows/install.ps1` — both create `.env` from the example automatically now.

## 9. Frontend structure

Chart primitives (`components/charts/`): `TrendChart` (time-series, Explorer-backed), `DistributionBar`, `DonutChart`, `RadarChartCard`, shared `ChartPanel` wrapper with the "?" metric-explain pattern (pulls from the same metrics registry the CLI's `netintel explain` command uses — one description source, two surfaces).
